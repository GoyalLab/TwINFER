## How the annotation filter is implemented

No changes to the twinfer package were needed for this part. `assign_twin_id`
and `_build_cross_time_twins` (in `correlation_functions.py`) group cells into
twins purely by the `clone_id` column. `preprocessing/build_annotation_filtered_inputs.py`
relabels `clone_id -> "{clone_id}__{Cell type annotation}"` before that
grouping happens, using labels from
`finalized_data/LARRY_data/annotated/filtered_annotated_k15.h5ad`
(`larry_raw_annotate.py`'s output: published Weinreb et al. labels where
available, KNN-transferred elsewhere). This silently blocks same-clone,
different-cell-type pairs from ever becoming twins, at both timepoints, with
zero package changes. Clone count goes 5,387 -> 7,635 after the split.

## Bug #3 found and fixed: z_reg_gated was effectively serial

While investigating why the 50-core SLURM jobs reported terrible efficiency
(user-supplied `sacct` report: **2.10% CPU efficiency of a 50-core
allocation, 10.60% of 64GB memory**), traced it to
`twinfer/inference/infer.py`'s `gated_regulation_details` loop (computes
`z_reg_gated`, the permutation-based heterogeneity-gated regulation
statistic): it looped over every gene pair **serially** in plain Python, and
`calculate_gated_regulation_statistic` itself (in `correlation_functions.py`)
loops over its `n_shuffles` permutation draws **serially** too -- unlike
every other null-generation stage in the file (step1, z_div, z_d_het, etc.),
which already chunk their shuffle draws across `n_cores_to_use` via
`joblib.Parallel(prefer="threads", require="sharedmem")` +
`threadpoolctl.threadpool_limits`. This was the real bottleneck: hundreds of
gene pairs x up to 5000 shuffles each, single-threaded, while the requested
cores sat idle.

**Fixed in `twinfer/inference/infer.py`**: the per-pair loop that computes
`gated_regulation_details` (search for `_one_gated_regulation`) now farms
pairs out across `n_cores` threads via the same
`Parallel(prefer="threads", require="sharedmem")` +
`threadpool_limits(limits=1, user_api="blas")` pattern already used elsewhere
in the package, instead of running one pair at a time. The original serial
loop is left commented directly above the replacement per this repo's
"comment out, don't delete" convention. Each pair still reseeds its own
`np.random.default_rng` independently (as before), so parallelizing across
pairs changes nothing numerically -- **verified bit-identical**: ran
`infer_with_twinfer` on a 5-gene subset at `n_cores=1` vs `n_cores=4`
(50 shuffles, `alpha_gene_gene_corr=alpha_stage3=0.9999`,
`z_score_threshold_*=0`) and diffed every `z_reg_gated` value: 0/10
mismatches.

The internal `n_shuffles` loop inside `calculate_gated_regulation_statistic`
itself (correlation_functions.py, the `for b in range(n_shuffles):` block)
is **still serial** -- only the outer per-pair loop was parallelized this
session. Further speedup is possible there (chunk shuffles across cores the
same way `_random_pair_null_chunk` etc. already do) but wasn't done.

A proper core-scaling benchmark to pick the "right" `N_CORES` was attempted
but abandoned: it was run on the **login node**, which reports 52 cores via
`nproc`/`os.sched_getaffinity` but is a shared, policy-throttled node --
the user correctly flagged this ("there aren't 50 cores in login node -
there are only 4") as not representative of an actual SLURM allocation. No
valid scaling number was obtained. User's final instruction: skip the
benchmark, just pick a reasonable core count and submit.
